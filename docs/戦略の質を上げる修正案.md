1. 今の状態
流れは ①入力 → ②収集 → ③事実シート → ④エージェント → ⑤画面 です。④では、4人の担当（物件・立地・価格・買い手）が事実の一部ずつを分析し、メインがまとめ、媒体が配分を決め、確認担当が点検します。モデルはすべて claude-haiku-5-5（effort medium）です。

これまでの6回の実行の記録（agent_calls・check_results）

1回の実行	7回の呼び出し、約1.5分、約0.02ドル
メインへの入力	約21,000トークン（事実シート全体と4つの分析）

作り直し	止めている（REBUILD = false）。見つけた問題は、そのまま画面に出る
費用は問題になっていない。問題は中身。

分析が事実の言い換えになっている。 例：立地担当が「1km以内にコンビニ24件…買い物がしやすい可能性が高い」と書く。「言い切らない」「事実だけを使う」「計算しない」などの決まりが多く、モデルが安全な言い換えに逃げる。
分けたことで、組み合わせた見立てができない。 物件担当は施設や災害を見られず、買い手担当は学区や施設を見られない。メインは結局、事実シート全体を読み直していて、4つの分析は下書き程度の役しかしていない。分けた分、情報が途中で落ちる。
決まりどうしがぶつかっている。 確認の指摘でいちばん多いのは「事実からその内容が言えない」（20件）。その中に「必要年収以上の割合を『買える見込み』と言い換えている」のように、設計で決めた言い方そのものを問題にしたものがある。
確認しても結果に生きていない。 作り直しを止めているので、確認に1回分（約17,000トークン）を使っても、画面は変わらない。
AIチャットに負けている理由

材料では勝っているのに、考える力と考え方を自分で絞っている。

2. 方針
正確さはプログラムと点検で守り、考えることはAIに任せる。

考える人を1人にし、賢くする。 全体を見る戦略担当を1人置き、claude-sonnet-5-5 にする。戦略を点検する確認担当も同じ claude-sonnet-5-5 にする（点検する側が見立てを読み違えて、正しい文を作り直させないため）。
縛るのではなく、後から確かめる。 機械で見られる決まりはプログラムで点検し、指示文から外す。数字・名前は事実からだけ使う決まりは残し、それ以外の見立ては自由に考えさせる。出したあとに点検で確かめ、合わなければ作り直す。
材料で差をつける。 AIチャットが持てないもの（地元の数字、似た取引の事例、BRUMBY様の知識、のちに社内の実績）を増やす。
CLAUDE.md の大事な決まりは変えない。

計算（距離・件数・相場比・返済額・金額）はプログラムで行う
取れなかった値は「取得できず」とし、推測で埋めない
物件ごとに外部と通信するのは、住所の緯度経度とAIの呼び出しだけ
事実シート、各エージェントの入力と出力、点検の結果は、物件ごとにDBに保存する
変えるのは、エージェントの構成と指示文、AIモデル（戦略担当と確認担当。媒体担当は Haiku のまま）。どれも了承を得てから設計まとめと CLAUDE.md を書き換える。

4. モデルと呼び出しの設定
4.1 戦略担当と確認担当は Sonnet 5.5（決定）
料金（100万トークンあたり、2026-10-30 に Anthropic の資料で確認）：Sonnet 5.5 は入力 $2.00・出力 $10.00。Haiku 5.5 は入力 $0.10・出力 $0.50（10万トークンを超えるプロンプトは $0.50・$2.50）。
見積もり：
- 戦略：入力 約2万トークン、出力 約8,000〜16,000トークン（考える分を含む）として、約0.12〜0.20ドル
- 確認：入力 約1万7,000トークン、出力 約4,000トークンとして、約0.07ドル
- 媒体：Haiku のまま、約0.003ドル
- 1回の実行は 0.2〜0.3ドル（30〜45円ほど）。PoCでは作り直さないので、これが上限の目安
- 実際の値は agent_calls で確かめる
考える量（effort）：Sonnet 5.5 は指定しないと high（Haiku 5.5 は medium）。今のコードは medium を指定している。戦略は medium と high の両方で試して決める。確認は medium から始める。
答えを断られたとき（stop_reason が refusal）：今のコードは失敗として記録する。試しの段階では、そのままでよい。
lib/agents/cost.ts をモデルごとの料金にし、呼び出しごとのモデルを agent_calls.model に残す。
4.2 ストリーミングと max_tokens
戦略の呼び出しは、分析とメインの答えを1回で作るので出力が大きくなる。今の max_tokens: 16000 には考える分も含まれ、途中で止まるおそれがある。

戦略の呼び出しはストリーミングで受け取り、最後にまとめて答えを取り出す。
max_tokens を 64,000 にする（上限は 128,000。ストリーミングなら大きくしても通信が切れない）。
受け取ったJSONは、今と同じく zod のスキーマで確かめ、形が崩れていれば失敗として記録する。
SDK の呼び方：使っている @anthropic-ai/sdk 0.131.0 で、messages.stream() に今と同じ output_config.format（zodOutputFormat）を渡せる。finalMessage() の parsed_output で答えが取れることを確かめた（2026-10-30）。
実行時間が延びるので、Vercel の関数の実行時間の上限を確かめる（今の戦略の API は maxDuration 300 秒）。

5.2 確認担当の指示文（案）
記録で多かった「設計で決めた言い方を問題にする」指摘をなくすため、「問題にしないこと」を書く。数字と名前は厳しく、見立ては矛盾がはっきりしているときだけ挙げる。

あなたは販売資料の校正担当です。渡された戦略の文章を一文ずつ、事実シートと照らし合わせてください。文章を書き直す必要はありません。
事実IDの有無、禁止語、媒体の件数と配分の合計は、プログラムが点検済みです。
文章には、事実と、不動産の一般的な知識にもとづく見立て（買い手にとっての意味、販売での使い方）が混ざっています。見立てがあること自体は問題ではありません。
点検すること：
1. 数字が事実と合っているか：価格・面積・距離・件数・割合・相場比・返済額・年数が、evidence の事実の値と一致するか。事実にない数字を作っていないか。
2. 名前が事実にあるか：施設名・店名・学校名・駅名・バス停名・路線名・地名が、事実シートにあるか。
3. 見立てが事実と矛盾していないか：例：駅まで直線2kmなのに「駅近」、1km以内に0件なのに「近くにある」、相場比が1.3倍なのに「割安」。
4. 災害を軽く書いていないか：浸水・土砂・液状化などの想定がある事実を「安全」「心配ない」と書いたり、懸念と対策から抜かしたりしていないか。
5. 価格や売れることを約束していないか：「この価格で売れる」「すぐ売れる」「値上がりする」など。
問題にしないこと：
- 一般的な見立てや売り方の提案。数字と名前を作っていなければよい
- 「必要年収以上の割合」から「買える見込み」を述べること
- 「割安」「相場なみ」「割高」、「売れやすい」「標準」「売れにくい」で始める書き方
- 文の長さや言い回しの好み
1と2は厳しく見る。3は、矛盾がはっきりしているときだけ挙げる。挙げるときは、どの事実IDの何と合わないかを problem に書く。
次の形のJSONだけを返してください。問題がなければ issues は空にします。
{"ok": true, "issues": [{"where": "appeals[1]", "check": 1, "problem": "問題の説明"}]}
合わせて直すこと：lib/agents/run.ts の AI_CHECK_NAMES を 1〜5 に合わせる。where の例は、戦略の新しい出力の形に合わせる。

5.3 作り直し
PoCでは作り直さない（REBUILD = false のまま。2026-10-30 小林さんと決定。費用と時間がもったいないため）。そのかわり、作り直すべき原因は残す。プログラムと確認担当が見つけた問題は、点検が求める扱い（作り直し・外す・記録だけ）のまま check_results に記録し、どの点検で、どの文に、何が問題だったかを後から数えられるようにする。IDのない文を外すことは続ける。作り直しを入れるかは、記録がたまってから決める。そのときの依頼文は、今の rebuild.txt の形（問題のある文だけ直し、ほかはそのまま返す）を土台に新しく作る（docs/指示文_第2版.md に依頼文の案は無い）。

7.3 社内の実績データ（PoCのあと）
このシステムで戦略を作った物件が、実際にいくらで、何日で売れたか、どの媒体から反響があったかを記録してためる。「似た物件はこう売れた」という、AIチャットには無い一番強い材料になる。結果を入れる表と画面が新しく要るので、PoCのあとに検討する。外に出してよい範囲も確かめる。

- PoCでは作り直さない。作り直すべき原因は check_results に残す（5.3）。費用の上限は決めず、1回 0.2〜0.3ドルの見込みを agent_calls で確かめる

- 比べ方の細部（各物件を何回ずつ動かすか、採点の基準を先に文章で決めるか）は今は決めない。仕組みを作り終えてから、AIチャットなどと比べるときに決める（9）
