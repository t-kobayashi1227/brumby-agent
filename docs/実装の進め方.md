# 実装の進め方

1段階ずつ進め、段階が終わるたびに利用者（小林さん）に結果を見せてから次へ進みます。仕様は `docs/設計まとめ.md` に従います。

## 0. 準備

- Next.js（App Router、TypeScript）のプロジェクトを作り、Vitest を入れます。
- Supabase のプロジェクトは利用者が作ります（クラウドの Supabase、またはローカルの Supabase CLI）。PostGIS 拡張を有効にします。
- `.env.local.example` を作り、利用者が `.env.local` に `ANTHROPIC_API_KEY`、`REINFOLIB_API_KEY`、`NEXT_PUBLIC_SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` を自分で書きます。
- 完了条件: `npm run dev` で空の画面が開き、サーバー側から Supabase に接続できます。

## 1. DBの形

- マイグレーションで次の表を作ります: 施設（位置つき）、区域（用途地域・学区・災害の形）、町の境界と統計、相場、前提値（金利など。項目・値・根拠・時点・適用開始日）、物件、事実シート、エージェントの実行記録、点検の結果。
- 位置と形の列には空間インデックスを付けます。
- 完了条件: `supabase db reset`（またはマイグレーションの適用）で表ができ、表の説明（`docs/DBの形.md`）があります。

## 2. データの取り込み

- `docs/設計まとめ.md` の「使用するデータ（37件）」を、1件ずつ取り込みます。取得先は `docs/参考/公的データ調査_2026-10-23.md` ほかにあります。
- 自動でダウンロードできないものは、ファイル名と置き場所（`data/raw/`）を利用者に伝えて、置いてもらいます。
- 通学区域一覧は、利用者が整備して置きます。
- 「DBを作るときに確かめること」の5点を、取り込みの中で確かめて結果を報告します。
- 区内の町の平均件数（施設の種類ごと）を、町の境界（No.39）から事前に計算して保存します。
- 完了条件: データごとの件数と時点の一覧を出せます。

## 3. 事実シートの作成（②と③）

- 住所から緯度経度を出します（国土地理院 住所検索API）。
- 周りの施設、区域の判定、町の統計、相場を PostGIS の SQL で引き、ローン計算を TypeScript で行い、③の形の事実シート（JSON）を作ります。
- ローン計算は、設計まとめの式と、候補ごとの代表年齢（10-24仮決め）に従います。
- 完了条件: 新潟市内の実在の住所3件で事実シートが作れ、利用者が値を確かめられます。ローン計算は見本（2,480万円 → 変動1.3%で月約6.6万円、必要年収約318万円。固定3.83%で月約9.7万円、約463万円）とテストで一致します。

## 4. エージェント（④）

- 7つのエージェントを、処理の流れどおりに動かします（4つの分析は同時に動かします）。
- 点検は、まずプログラムで形を確かめ、次に確認エージェントが中身を見ます。問題のある文は1回だけ作り直します。
- すべての入力・出力・費用をDBに保存します。
- 完了条件: 段階3の3件で戦略のJSONが出て、1物件あたりの費用が分かります。

## 5. 画面（①と⑤）

- ①の入力画面（地図でピンを直せる形）と、⑤のレポート画面（エリア分析・販売戦略・根拠データの3つのタブ）を作ります。
- 予算シミュレーション、注記、出典の一覧は設計まとめのとおりにします。
- 地図の表示には OpenStreetMap か国土地理院の地図タイルを使い、出典を表示します。
- 完了条件: 入力から表示まで、画面だけで1物件を通せます。

## 6. 試しと指示文の見直し

- 新築・中古、駅近・郊外、割安・割高が混ざるように3〜5件で動かし、出力と費用を表にまとめます。
- 指示文の直し方は、出力を見ながら利用者と決めます。
