## 1. 誤り・決まりへの違反

### 1.1 OSM の分類の誤り

**直すところ：** `scripts/ingest/jobs/osm.ts`

- ファイルの先頭に補正表を置く。コンビニ（convenience）と付いた店だけを対象にし、名前で種類を直す

  ```ts
  /** OSM のタグの誤りを名前で直す（fclass が convenience でも、スーパーの名前ならスーパー）。docs/事実シートの修正_実装案.md 1.1 */
  const NAME_FIXES: { fclass: string; pattern: RegExp; kind: string }[] = [
    { fclass: "convenience", pattern: /イオン|原信|ウオロク|ピアレ|清水フードセンター/, kind: "スーパー" },
  ];
  ```

- 種類を決める処理を `kindOf(fclass, name)` に切り出して export し、テストから呼べるようにする。直したときは `attrs.種類の補正 = "名前から（OSM は convenience）"` を残す
- 直した件数を `log` と `check("名前で種類を直した店", …)` に出し、`docs/data-ingest-records.md` に記録する

**入れ直す順：** `osm` → `d29-large-stores`（OSM に同じ種類の店があるかを見るため、OSM の後）→ `ward-averages`

**テスト（tests/ingest-files.test.ts などに足す）：** 「イオンスタイル上所」＋convenience → スーパー。「セブンイレブン新潟上所店」＋convenience → コンビニ。「イオン」を含む名前でも supermarket の店はスーパーのまま。

### 1.2 大規模小売店舗の位置のずれ（修正案の「重複」を置き換える）

同じ種類の中の重複は無いので、修正案の「名前が似ていて 150m 以内ならまとめる」処理は作らない。代わりに、D29 の位置を直す。

**直すところ：** `scripts/ingest/jobs/d29-large-stores.ts`

- 住所から出した位置が町丁目の代表点になる店は、近く（500m 以内）に**名前の合う**店が OSM（D28 のスーパー・ドラッグストア）か医療情報ネット（D30 の薬局）にあれば、その位置を使う。OSM を先に、無ければ D30
- 名前の比べ方：NFKC にそろえ、空白・「株式会社」「㈱」・「薬局」を除き、「ウェ」を「ウエ」にしたうえで、片方がもう片方を含めば同じ店
  - 「ウエルシア新潟上所中店」（D29）・「ウェルシア新潟上所中店」（D28）・「ウエルシア薬局　新潟上所中店」（D30）は同じになる
  - 「ウエルシア薬局」（D28、店名なし）は、店名の無い名前どうしの誤りを防ぐため、**支店名（「〜店」）を含まない名前は比べない**
- 位置を借りたときは `attrs.位置 = "OSM の同じ店の位置"`（または「医療情報ネットの同じ店の位置」）とし、元の推定位置を `attrs.住所から推定した位置` に残す
- 取り込み時に行う（修正案 6 の「取り込み時か物件ごとか」は、取り込み時を推す。区の平均にも効くため）

**入れ直す順：** `d29-large-stores` → `ward-averages`

**テスト：** 名前のそろえ方（ウエルシア／ウェルシア、全角・半角、空白、「薬局」）。支店名の無い名前は合わないこと。500m の境目（499m は借りる、501m は借りない）。

修正案にあった「薬局（D30）とドラッグストア（D28）は種類が違うのでまとめない」は、そのままでよい。事実の名前「ドラッグストア」「薬局」も今のままでよいと考える。

### 1.3 バス停を停留所名でまとめる

P11 は事業者ごとに点があるので、同じ名前の点は同じ停留所の別の事業者とみなす。

**直すところ：**

- `lib/facts/collect.ts` の `collectTransport`
  - 1km以内の一覧：同じ名前をまとめ、距離はいちばん近い点、系統数は**足す**（事業者が違うので二重に数えない）
    ```sql
    select name, min(extensions.st_distance(geog, ${pt})) as distance_m, sum((attrs->>'系統数')::int) as routes
    from facilities where kind = 'バス停' and extensions.st_dwithin(geog, ${pt}, ${NEAR_M})
    group by name order by distance_m
    ```
  - 最寄りバス停（T-05）：上の結果の1件目を使う。1km以内に無いときだけ今の最寄りの SQL を使う（同じ名前の別の場所の停留所が市内にあるため、1km の外は名前でまとめない）
  - 事業者の名前も最寄りに添える（例：「ユニゾンプラザ前 直線290m（系統数 2：新潟交通・新潟交通観光バス）」）。要るかどうかは決めてください
- `scripts/ingest/ward-averages.ts`：バス停だけ名前の数で数える
  ```sql
  select count(distinct case when k.kind = 'バス停' then f.name else f.id::text end) from facilities f ...
  ```

**テスト：** 同じ名前の2点が1件になり、距離は近いほう、系統数は合計になること（組み立ての部分を関数に切り出して tests/facts.test.ts でテストする）。

**影響：** この物件の 1km以内は 20件 → 14件になる。区の平均（32.9件）も下がる。

### 1.4 乗降客数の「データなし」

**直すところ：** `lib/facts/build.ts` の `transportFacts`（今の 531 行目）

```ts
!s ? null : typeof s.passengers === "number" ? `${formatNumber(s.passengers)}人` : s.passengers,
```

`s.passengers` が null（S12 に駅が無い）なら値が null になり、`fact()` が状態を「取得できず」にする。

**「公表なし」（修正案 6）：** 値として残すのを推す。S12 に駅があり、乗降客数が公表されていないことは分かっている事実で、「取れなかった」とは違う。AI が「小さい駅」と読みすぎないよう、値は「公表なし（国土数値情報の駅別乗降客数に数値の記載なし）」と書く。

**テスト：** passengers が null で状態「取得できず」、"公表なし" で値が残り状態「取得」。

### 1.5 1km の境目の表示

**推す案：** 修正案の案A を、`formatDistance` そのものに入れる。1km未満で丸めて 1000m になるときは 990m にする。

```ts
if (meters < 1000) return `直線${Math.min(990, Math.round(meters / 10) * 10)}m`;
```

1km以内の一覧に限らず、どこでも「1km未満なのに1000m」は出なくなる。ずれは最大 9m で、今の丸めのずれ（5m）とほぼ同じ。案B（一覧だけ 1m 単位）は書き方が2通りになるので推さない。

**テスト（tests/facts.test.ts）：** 994 → 990m、995 → 990m、999 → 990m、1000 → 1.0km、1001 → 1.0km、1049 → 1.0km、1050 → 1.1km。

## 2. 誤った見立てに導きやすい点

### 2.1 相場比の補い

**推す案：** 案A（広さの近い取引だけの相場）だけを足す。案B は足さない。

- 0 章のとおり、この物件では広さをそろえると相場は下がり、相場比は上がる見込み。「1.81倍は土地が広いせい」という見立ても、事実で確かめられるようにするのが大事で、それには取引の実データ（案A）が合う
- 案B は、基準地の ㎡単価（標準的な広さの土地）に広い土地の面積を掛けるので、広い土地ほど土地の目安が高く出て、建物分の目安が小さく出る。「建物分 約1,461万円」は、エージェントが確かな値として使ってしまうおそれがある
- 相場比を2つにしないため、案A は「相場比」ではなく「広さの近い取引の相場（中央値と件数）」として出し、相場比は M-02 の1つのままにする

**範囲：** 土地面積 0.7〜1.3倍 **かつ** 延床面積 0.7〜1.3倍。土地だけだと、延床の小さい家が混ざる。件数が足りないときは、年の範囲を `selectMarket` と同じ決まりで広げる。それでも 10件未満なら「件数が少ない」、0件なら「取得できず」

**直すところ：**

- `docs/相場の出し方変更.md` に 3.8 として追記（先に）
- `lib/facts/build.ts`：`selectMarket` と同じ取引の一覧（`MarketInput` の取引）から、広さで絞った中央値を出す関数 `similarSizeMarket(trades, property)` を作る。SQL は増やさない（`collectMarket` が引いた取引を使う）
- 事実の例：「広さの近い取引の延床坪単価（中央区・築20〜29年・延床146〜272㎡・土地243〜452㎡）中央値 ○万円/坪（○件）」

**テスト：** 範囲の境目（0.7倍ちょうど・1.3倍ちょうどを含む）、件数 0・9・10 件の書き方。

### 2.2 必要年収以上の割合が全国の分布

**今すぐ直す：** `buyerFacts` の項目名と出典に「全国」を入れる。

- 項目：「必要年収以上の世帯の割合（変動○%、全国の中古戸建の買主の年収分布から）」
- 出典：「住宅市場動向調査（全国、中古戸建を買った世帯の年収分布）から計算」

**あとで調べる：** 新潟県の年収分布。住宅・土地統計調査の「世帯の年間収入階級」（都道府県別・持ち家）が候補。`docs/参考/` に調査メモを作ってから決める。

### 2.3 ターゲット候補ごとの返済の目安をまとめる

**確かめたこと：** `prompts/buyer.txt` は、出力の text の先頭に「【候補名】」を付けるよう指示しているが、事実の ID や事実の項目名で候補を引いてはいない。まとめた行にも候補名を並べれば、指示文は変えなくてよい。

**直すところ：** `buyerFacts` の候補ごとのループを、返済期間でまとめる。

- 返済期間が同じ候補を1行に：「【若い夫婦・小中学生のいる家族・単身・親と同居】の返済の目安（返済期間35年）」
- 並びは返済期間の長い順。候補の並びは `target_candidates` の順

**テスト：** 代表年齢から返済期間が同じになる候補が1行にまとまり、違う候補は別の行になること。

### 2.4 住み替え層の頭金

**直すところ：**

- 前提値の表（`assumptions`）に行を足すマイグレーション。key は「住み替えの頭金の割合」。値と根拠は、住宅市場動向調査の二次取得者（住み替え）の自己資金比率から決める（30%・50% は根拠を確かめてから決める仮の値）
- `target_candidates` に、住み替えの頭金を使う候補の印（`uses_resale_down_payment boolean`）を足し、【50代の住み替え】【60歳以上】に付ける。候補名で判定しない
- `buyerFacts`：印のある候補は、通常の頭金（10%）の行に加えて、住み替えの頭金での返済額・必要年収を1行足す
- `docs/設計まとめ.md`「買い手・ローンの前提」に追記

**テスト：** 頭金30%・50% の借入額・月々の返済額・必要年収（`calcLoan` に downPaymentPct を変えて渡すだけなので、tests/loan.test.ts に値を足す）。

### 2.5 買主の年代に「不明」を足す

**直すところ：** `buyerFacts` の「買主の年代」で、合計が 100% に足りないときは、残りを「無回答など 4.8%（100%から引いた残り）」として末尾に足す。足す前に、報告書の表に無回答の欄があるかを確かめる（無回答なら「無回答」と書く）。

**テスト：** 合計 95.2% で「無回答など 4.8%」が付き、合計 100% なら付かないこと。
