## 4. ① データの取り込みと版の管理

### 4.1 取り込みの流れ
```
取得 → 生データを保存 → 形を整えて読み込む（status=loading） → 件数を確認 → 使用中に切り替える（active）
```
- コマンドの例：`npm run ingest -- reinfolib-transactions --pref 15 --from 2015Q1`
- 何度実行しても結果が二重にならないようにする。
- 既存の版は上書きしない。新しい版を横に読み込んでから切り替える。古い版は `archived` にして残す。
- 生データの保存先：PoCでは Supabase Storage（使うサービスを増やさないため）。本番でR2に移すかはStep 2で判断する。

### 4.2 データの種類ごとの持ち方
| データ | 持ち方 | PoCでの範囲 | 保存先 |
|---|---|---|---|
| 町丁目の境界の形＋国勢調査2020（小地域） | 先に取り込む | 新潟県 | `areas`、`census_values` |
| 取引価格（XIT001） | 先に取り込む | 新潟県・過去10年 | `transactions` |
| 地価公示・地価調査（XPT002） | 先に取り込む | 新潟県・過去10年 | `land_prices` |
| 施設・学区・防災・将来人口・都市計画（XKT系） | 初回に取得して保存（地図タイル単位） | テスト物件の周り半径3km＋余白 | `tile_cache` → `facilities`、`school_districts`、`hazard_zones`、`pop_mesh`、`zoning` |
| 商業施設（OSM Overpass） | 初回に取得して保存 | テスト物件の周り半径3km | `facilities`（source=osm） |
| 住所 → 緯度経度 | その都度呼ぶ。結果は物件に保存する | — | `properties.geom` |

### 4.3 版の管理
```sql
dataset_versions (
  id, source, dataset, coverage, period,
  fetched_at, source_published_at, attribution, raw_uri,
  row_count, status  -- loading | active | archived
)
```
- データの行にはすべて `dataset_version_id` を付ける。
- 分析の実行（`analysis_runs`）には、使った版のIDを記録する。

### 4.4 取り込みの記録（確認1の材料）
取り込むたびに、件数・空欄の割合・物件の周りで取れた件数を `ingest_logs` に残す。

### 4.5 序盤に確かめること
- **XIT001（取引価格）には緯度経度がなく、地区名しかない。** 地区名を町丁目に結びつける処理（表記ゆれの吸収）を作る。XPT001の位置情報で代わりにできるかも実測する。
- **APIキーを申請する**：不動産情報ライブラリとe-Stat。キックオフ（10/5）の前に済ませる。
- XKT系の個々のAPI IDと中身の対応を、公式マニュアルで確かめる（`データ取得API一覧.md` の対応には推定が含まれる）。

## 5. ② 集計と事実カード

### 5.1 事実カード
```sql
facts (
  id, run_id, key,            -- 例：target.family_with_children_ratio
  value, unit, comparison,    -- comparison：比べる値（市の平均など）
  scope,                      -- 例：{"type":"radius","meters":1000} / {"type":"ward","name":"中央区"}
  basis,                      -- 例：{"households":2140} / {"n":24,"period":"2023Q2-2026Q1"}
  status,                     -- ok | insufficient | not_available
  kind,                       -- fact（集計）| decision（ルールの判断）
  dataset_version_ids, attribution
)
```
- レポートでは、カード1枚ごとに番号（例：`F-07`）を振って表示する。
- データが足りない場合もカードを作る（`status=insufficient`）。黙って空欄にしない。

### 5.2 分析の実行
```sql
analysis_runs (id, property_id, params, dataset_version_ids, rules_version, status, created_at)
```
- `params` の例：`{"radius_m":1000,"price_min_n":10,"price_years":3}`
- 条件を変えて再実行すると、新しい実行として記録する。古い結果は残し、2回分を並べて比べられるようにする。

### 5.3 集計の部品（`lib/analyzers/`）
| 部品 | 範囲 | 作るカード |
|---|---|---|
| ① 人口構成 | 半径（初期値：中心部1km、郊外・周辺3km） | 年齢層、夫婦と子どもの世帯、借家の割合。市の平均と比べる |
| ② 将来人口 | 250mメッシュ → 半径 | 2035年までの子育て世代の増減 |
| ③ 相場 | 町丁目 → 地区 → 区・市 | 中央値、四分位、件数、範囲をどこまで広げたか、地価の推移 |
| ④ 周辺施設 | 学区＋距離 | 学区、最寄りの小・中学校と保育園までの距離、施設の数、駅 |
| ⑤ 防災 | 物件の地点 | 浸水の想定、土砂災害、液状化 |
| ⑥ 競合物件 | 手入力（3件まで） | 価格差、面積あたりの価格の差、特徴の違い |

集計の約束事：
- 半径の集計は、町丁目の値を円と重なる面積の割合で割り振る（`ST_Intersection` / `ST_Area`）。
- 相場は、直近の期間で `price_min_n` 件以上になるまで範囲を広げ、使った範囲をカードの `scope` に残す。
- 距離はPoCでは「直線距離×1.3」を徒歩の目安として表示する。道路に沿った距離にするかは本番で判断する。
- 防災のカードは「確認を促す」表現にし、出典と時点を必ず付ける。

## 6. ③ ルールとAI

### 6.1 ルール表
```sql
rules (
  id,           -- R-21
  kind,         -- total_budget | media_weight | min_spend | target_score
  condition,    -- {"fact":"target.age_30_49_ratio","op":">","than":"comparison","delta":0.05}
  effect,       -- {"media":"instagram","weight":2}
  note,         -- 理由（BRUMBY様の言葉で書く）
  version, updated_by, updated_at
)
```
- 条件は「事実カードの値と、定数または比べる値との単純な比較」だけにする。
- 計算の手順（毎回同じ）：
  1. 狙う層の候補（あらかじめ用意したリスト）に点数を付けて順位を出す
  2. 総予算を決める
  3. 媒体の重み → 比率 → 最低額と単位を当てはめる → 千円単位に丸める
  4. 効いたルールを記録する
- 結果は `kind=decision` の事実カードとして保存する。
- 最初は仮のルールから始め、打ち合わせのたびに直す。変更の理由は `note` と版で残す。

### 6.2 AI（`lib/ai/`）
- モデル：まず Claude Sonnet 5。文章の質が足りなければ Opus 5.5 と比べる。
- AIに渡すもの：物件情報、事実カード、判断カード、競合物件（すべて番号付きのJSON）。
- AIに任せること：訴求ポイントの言葉づくり、狙う層の人物像、予算配分の理由の説明（金額は変えない）、競合との違いの説明。
- AIへの約束事：数字には必ずカードの番号を付ける。カードにない数字を作らない。データが足りないカードは「判断できない」と書く。
- 出力：決まった形のJSON（セクション → 文 → 引用したカードの番号）。
- 生成した文章は `narratives` に実行ごとに保存し、画面を開き直しても作り直さない。

### 6.3 検証
1. 文中の数字（%、万円、m、分、件など）を抜き出す
2. 引用したカードの値と一致するか確かめる（四捨五入の差は許す）
3. 一致しなければ、ずれの内容を伝えて1回だけ作り直させる
4. それでも一致しなければ、その段落に「要確認」の印を付けて表示する

| `/strategy`（タブ：総合評価／媒体戦略・予算） | レポートの中心。4つの答え、AIの文章、予算配分、効いたルール、出典 |

画面の共通の約束事：
- 数字にカーソルを合わせると事実カード（値・範囲・件数・出典・時点）を表示する。
- 地図：MapLibre GL＋国土地理院の淡色地図（出典を表示する）。物件、半径の円、施設、浸水想定を重ねる。
- 条件を変えて再実行するときは、段階ごとの進み具合を表示する（集計 → ルール → AI → 検証）。前回の結果と並べて比べる。

### 7.1 プロトタイプの表示項目とデータ源の対応（要調整）
プロトタイプの仮データには、公開データでは出せない項目がある。本物のデータをつなぐときに、置き換えるか削るかをBRUMBY様と決める。

| プロトタイプの項目 | 状況 | 案 |
|---|---|---|
| 競合物件数（合計32件） | ポータルのデータが必要。自動収集はしない方針 | 「手入力の競合3件」と「直近の取引件数」に置き換える |
| 成約件数の前月比、平均販売期間 | 公開データにない（取引価格は四半期ごと・約半年遅れ、販売期間はない） | 四半期ごとの件数の推移に置き換える。販売期間は削る |
| 狙う層の世帯年収 | 国勢調査に年収はない。住宅・土地統計調査は市区町村単位まで | 市区町村単位の参考値として出すか、削る |
| 周辺環境のスコア（4.5など）、総合評価「A」 | 計算の根拠がない | ルール表で点数を計算する（判断カード）か、削る |
| 商業施設・飲食店の件数 | 不動産情報ライブラリにない | OSMで数える（網羅度は確認1で実測する） |
| 成約事例の一覧（物件名・販売日数） | 取引価格は地区名単位で、個別の物件は特定できない | 「地区・面積・価格・時期」の取引一覧に置き換える |

## 8. エラーとデモへの備え
- 打ち合わせの前に、テスト物件すべての分析を実行しておく。打ち合わせ中に動かすのは、条件を変えた再実行だけにする。
- AIが失敗しても、事実カードと判断カードだけでレポートを表示する（文章の欄に「生成できませんでした」と出す）。
- APIの取得に失敗したら、間隔を空けて数回やり直す。それでも失敗したら、その版は `loading` のまま切り替えない。
- データが足りない場合は `status=insufficient` のカードを作り、レポートに正直に出す。

## 9. テスト
- 集計の部品：小さな固定データ（町丁目3つ、取引10件 など）で「この入力ならこのカードになる」を確かめる。
- ルールエンジン：条件と効果の組み合わせごとに、期待する配分になるかを確かめる。
- 検証：作られた数字を含む文章、四捨五入の差がある文章を用意し、正しく見分けられるかを確かめる。
- AIの文章：テスト物件5〜10件で、検証を通る割合を記録する（本番の要件の材料）。
