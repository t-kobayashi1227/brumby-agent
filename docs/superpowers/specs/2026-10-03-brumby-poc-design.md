## 1. 目的と範囲

### 1.1 PoCで確かめること（提案書P.11）
| | 確かめること | 成果物 |
|---|---|---|
| 確認1 | 公開データは足りるか（新潟市の中心部・郊外・周辺の市町村、実物件5〜10件） | データ測定の結果（測定画面と取り込みの記録）。判定は10/9（D19） |
| 確認2 | 実務で使える戦略が出るか | 操作できる叩き台、戦略の評価結果（5段階×4観点、D18）、本番開発の要件 |

### 1.2 デモの形
- 基本は**クラウドネイチャーが操作し、BRUMBY様が見て評価する**。途中でBRUMBY様にも操作してもらう（D16）。
- Vercelにデプロイし、Basic認証で守る（D5）。ログイン・権限・課金は対象外。
- 評価者はBRUMBY様のみ。取引先2〜3社による出力確認はPoCでは行わない（D16）。

### 1.3 やらないこと
- ログイン、権限、課金（アクセス制限はBasic認証のみ）
- ポータルサイトからの自動収集（提案書P.6の方針）
- PDFファイルの出力（ブラウザの印刷で代用。印刷用の画面は作る、D27）
- 制作・広告の相談への導線、スマホ対応
- 販売モニター、プラン・オプション、お知らせ（画面は残すが、ナビから外す。D27）
- 組織（`organization_id`）による分離（D32）

| D31 | **取り込みの記録を細かくする。** `ingest_logs` に `failure_kind`（auth／rate_limit／network／other）、`published_on`（公開年月）を足し、取得成功率と鮮度を出せるようにする | 社内PDFの測定項目（取得成功率、鮮度）に合わせる |

| D34 | 分析の実行は、段階（集計→ルール→AI→検証）ごとに別の呼び出しにし、`analysis_runs.stage` を画面がポーリングして進み具合を出す。1回の呼び出しがVercelの実行時間の上限を超えないようにする | AI生成が数十秒かかるため |

## 3. 全体の構成

```
公開データAPI ─┐
物件情報 ──────┼→ ① DB（Supabase＋PostGIS、データは版つき）
競合物件(≤3) ──┘          │
                          ▼
              ② 集計の部品 → 事実カード（値・範囲・件数・出典・版）
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
     ③ ルール表 → 判断カード   ③ AI（Claude）：カードを引用して説明文を作る
     （狙う層・訴求・予算配分）         │
              │                  検証：数字・比較語・種別をカードと照合
              └───────────┬───────────┘
                          ▼
              ④ 販売戦略レポート（/strategy、/report）
```

### 3.1 リポジトリの構成（既存のNext.jsをルートに置いたまま追加する）
```

lib/db/                  DB接続（postgres.js、プーラー経由）
lib/analyzers/           集計の部品（物件と条件を受け取り、事実カードを返す）
```

## 4. ① データの取り込みと版の管理

### 4.1 取り込みの流れ
```
取得 → 生データを保存 → 形を整えて読み込む（status=loading） → 件数を確認 → 使用中に切り替える（active）
```
- コマンドの例：`npm run ingest -- reinfolib-transactions --pref 15 --from 2015Q1`
- 何度実行しても結果が二重にならないようにする。
- 既存の版は上書きしない。新しい版を横に読み込んでから切り替える。古い版は `archived` にして残す。
- 生データの保存先：Supabase Storage（`ingest-raw`、非公開）。

### 4.2 データの種類ごとの持ち方
| データ | 持ち方 | PoCでの範囲 | 保存先 |
|---|---|---|---|
| 町丁目の境界の形＋国勢調査2020（小地域） | 先に取り込む | 新潟県 | `areas`、`census_values` |
| 取引価格（XIT001） | 先に取り込む | 新潟県・過去10年 | `transactions` |
| 地価公示・地価調査（XPT002） | 先に取り込む | 新潟県・過去10年 | `land_prices` |
| 施設・学区・防災・将来人口・都市計画（XKT系） | 物件の登録時に、周りの地物だけを取得して保存 | 物件の周り（半径3kmまたは300m） | `geo_features`、`property_fetches` |
| 商業施設（OSM Overpass） | 同上 | 物件の周り半径3km | `geo_features`（api_id=OSM） |
| 住所 → 緯度経度 | その都度呼ぶ。結果は物件に保存する | — | `properties.geom` |

使うAPIごとの詳細は `使用API一覧.md`。

### 4.3 版の管理
```sql
dataset_versions (
  id, source, dataset, coverage, period,
  fetched_at, source_published_at, attribution, raw_uri,
  row_count, status  -- loading | active | archived
)
```
- データの行にはすべて `dataset_version_id` を付ける。
- 分析の実行（`analysis_runs`）には、使った版のIDを記録する。

### 4.4 取り込みの記録（確認1の材料）
取り込むたびに、件数・空欄の割合・物件の周りで取れた件数を `ingest_logs` に残す。D31で `failure_kind`、`published_on` を足す。物件ごとの取得の記録は `property_fetches`。

### 4.5 データ測定（確認1）と10/9の判定
- **物件 × 集計の部品の表**に、取れた／不足／なし、件数を出す（測定画面）。
- 判定はD19の基準。測定画面を待たず、10/9は取り込み済みデータのSQLと `ingest_logs`、`property_fetches` でまとめる。
- 測定の項目：取得成功率、カバレッジ（物件×部品）、比較可能件数、鮮度（公開年月と実施日の差）、空間精度、利用条件（社内PDFの指標に対応）。

### 4.6 序盤に確かめること
- XIT001の地区名と町丁目の対応は、宅地で98.2%（完全一致94.3%＋前方一致3.9%。2026-10-03実測、D13）。詳細は `docs/data-notes.md` の4章。
- 新潟市・長岡市の小・中学校区（XKT004/005）は**データがない**。学区の訴求は新潟市では出せない。
- APIキー（不動産情報ライブラリ、e-Stat）は取得済み。利用条件は `使用API一覧.md` の確認欄で管理する。

## 5. ② 集計と事実カード

### 5.1 事実カード
```sql
facts (
  id, run_id,
  seq,                        -- 画面の番号（F-07 の 7）
  key,                        -- 例：target.family_with_children_ratio
  value, value_text, unit,    -- value_text：学区名など数字でない値
  comparison,                 -- 比べる値（市の平均など）
  scope,                      -- 例：{"type":"radius","meters":1000} / {"type":"ward","name":"中央区"}
  basis,                      -- 例：{"households":2140} / {"n":24,"period":"2023Q2-2026Q1"}
  status,                     -- ok | insufficient | not_available
  kind,                       -- fact（集計）| decision（ルールの判断）
  dataset_version_ids, attribution
)
```
- レポートでは、カード1枚ごとに番号（例：`F-07`）を振って表示する。
- データが足りない場合もカードを作る（`status=insufficient`）。黙って空欄にしない。
- カードのkey一覧は `database-guide.md`。D21で `target.age_20_39_ratio`、`target.age_65plus_ratio` を足す。

### 5.2 分析の実行
```sql
analysis_runs (id, property_id, params, dataset_version_ids, rules_version, status, stage, created_at)
```
- `params` の例：`{"radius_m":1000,"price_min_n":10,"price_years":3,"min_top_score":2,"tie_margin":0}`
- 条件を変えて再実行すると、新しい実行として記録する。古い結果は残し、2回分を並べて比べられるようにする。
- 再現性の確認（2物件×3回）は、同じ条件で3つの実行を作って比べる。

### 5.3 集計の部品（`lib/analyzers/`）
| 部品 | 範囲 | 作るカード |
|---|---|---|
| ① 人口構成 | 半径（初期値：中心部1km、郊外・周辺3km） | 年齢層（20〜39・30〜49・65歳以上）、夫婦と子どもの世帯、借家の割合、一戸建の割合。市の平均と比べる |
| ② 将来人口 | 250mメッシュ → 半径 | 2035年までの人口と年齢層の増減 |
| ③ 相場 | 物件のある地区（町・大字＝その町丁目を含む地区） → 周りの地区 → 区・市 | 中央値、四分位、件数、範囲をどこまで広げたか、地価の推移 |
| ④ 周辺施設 | 学区＋距離 | 学区、最寄りの小・中学校と保育園までの距離、施設の数、駅、用途地域 |
| ⑤ 防災 | 物件の地点 | 浸水の想定、土砂災害、液状化 |
| ⑥ 競合物件 | 手入力（3件まで） | 価格差、面積あたりの価格の差、特徴の違い |

集計の約束事：
- 半径の集計は、町丁目の値を円と重なる面積の割合で割り振る（`ST_Intersection` / `ST_Area`）。D26の注記を画面に出す。
- 相場は、直近の期間で `price_min_n` 件以上になるまで範囲を広げ、使った範囲をカードの `scope` に残す。
- 距離はPoCでは「直線距離×1.3」を徒歩の目安として表示する。道路に沿った距離にするかは本番で判断する。
- 防災のカードは「確認を促す」表現にし、出典と時点を必ず付ける。

## 6. ③ ルールとAI

### 6.1 ルール表
```sql
rules (
  id,           -- R-21、R-T01 など
  kind,         -- total_budget | media_weight | min_spend | target_score | appeal_score
  condition,    -- {"fact":"target.age_30_49_ratio","op":">","than":"comparison","delta":0.05,
                --  "when":{"property_type":["新築戸建"]}}
  effect,       -- {"media":"instagram","weight":2} / {"candidate":"family","score":1} / {"appeal":"school_near","score":1}
  note,         -- 理由（BRUMBY様の言葉で書く）
  enabled, version, updated_by, updated_at
)
target_candidates (id, label, description, property_types, sort_order, enabled)    -- 狙う層の候補（D22）
appeal_items      (id, label, description, needs_facts, property_types, enabled)   -- 訴求の素材（D23）
```
- 条件は「事実カードの値と、定数または比べる値との単純な比較」だけにする。任意で `when`（物件種別）を付けられる。
- 計算の手順（毎回同じ）：
  1. 狙う層の候補に点数を付けて順位を出す（`狙う層の設計.md`）
  2. 訴求の素材に点数を付け、上位3つを選ぶ（D23）
  3. 総予算を決める：入力があればそれを使い、なければ `total_budget` ルールの提案値（D15）
  4. 媒体の重み → 比率 → 最低額と単位を当てはめる → 千円単位に丸める
  5. 効いたルールを記録する
- 結果は `kind=decision` の事実カードとして保存する。
- 最初は仮のルールから始め、打ち合わせのたびに直す。変更の理由は `note` と版で残す。
- ルールは `/rules`（D14）で見て、追加・変更・削除する。仮のルールは `npm run seed-rules` で入れる（すでにある番号は上書きしない）。

### 6.2 AI（`lib/ai/`）
- モデル：まず Claude Sonnet 5。文章の質が足りなければ Opus 5.5 と比べる。
- AIに渡すもの（D28で最小化）：物件ID・価格・面積・間取りなど（物件名と詳しい住所は渡さない）、事実カード、判断カード（順位・選ばれた訴求・予算配分）、競合物件。すべて番号付きのJSON。
- AIに任せること：訴求の言い換え、狙う層の人物像、予算配分の理由の説明（金額は変えない）、競合との違いの説明、アクションプラン（1週目／2〜4週目、見直しの目安）。
- AIにさせないこと：順位・訴求・金額を変える、カードにない数字を作る、属性を断定する（D29）。
- 出力：決まった形のJSON（セクション → 文 → 文の種別 → 引用したカードの番号）。
- セクション：物件の特徴・立地／想定ターゲット／訴求・チャネル／広告予算案／アクションプラン／不確実性と根拠（事実・推定・提案を区別）。
- 生成した文章は `narratives` に実行ごとに保存し、画面を開き直しても作り直さない。`input_tokens`、`output_tokens`、`duration_ms`、`model`、`prompt_version` も残す（D17）。

### 6.3 検証（D24）
1. 文の種別を確認する：`numeric`（数値）／`qualitative`（定性）／`proposal`（提案）。
2. `numeric`：文中の数字（%、万円、m、分、件など）を抜き出し、引用したカードの値と照合する（四捨五入の差は許す）。引用がなければ不合格。
3. `qualitative`：引用が1つ以上あること。比較語（多い・少ない・高い・低い・広い・上回る など）は、引用したカードに `comparison` がある場合だけ許す。
4. 禁止表現の確認：断定（「必ず売れる」）、属性の決めつけ、カードにない設備や距離（未入力のものを作らない）。
5. 不合格なら、不合格の内容を伝えて1回だけ作り直させる。それでも不合格なら、その段落に「要確認」の印を付けて表示する。
6. 検証の結果は `narratives.validation` に段落ごとに保存する（合格率はP3の材料）。

### 6.4 訴求の素材（D23の補足）
`appeal_items` の初期の例（直せる）：小・中学校が近い（`facility.elementary_nearest`）／保育園・幼稚園が多い（`facility.nursery_count`）／駅が近い（`facility.station_nearest`）／住居系の用途地域で落ち着いた環境（`area.zoning`）／相場より割安（`market.price_gap`）／地価が上昇しているエリア（`land.trend_5y`）／周辺の子育て世帯が多い（`target.households_with_under18_ratio`）／競合より土地が広い（`competitor.land_area_gap`）／ZEHなど物件の仕様（`properties.features`、物件の入力から）。
- 素材ごとに「必要なカード（`needs_facts`）」があり、そのカードが `ok` でない素材は選ばれない（学区は新潟市では選ばれない）。

## 8. データ不足とエラーの扱い

| 状況 | 画面・AIの扱い |
|---|---|
| 競合が未入力 | 競合の項を「未入力」と表示。競合に関する文は作らない |
| 相場の取引が `price_min_n` 件未満 | `insufficient`。「判断できない」と書き、「適正価格」を断定しない |
| 学区データがない（新潟市・長岡市） | 学区は `not_available`。学区を訴求に使わない |
| 国勢調査の秘匿・欠損 | その指標は `insufficient`。候補の満点から外す（`狙う層の設計.md`） |
| 周りのデータ（防災・施設）を取っていない物件 | `not_available` と理由を表示 |
| 全候補の点が低い | 「エリアの特徴からは絞り込めない」の判断カード |
| AIが失敗・形式崩れ | 事実カードと判断カードだけでレポートを表示し、文章の欄に「生成できませんでした」と出す |
| 外部APIが失敗 | 間隔を空けて数回やり直す。失敗したら版は `loading` のまま切り替えない。失敗の種類を `ingest_logs.failure_kind` に残す |

- 打ち合わせの前に、テスト物件すべての分析を実行しておく。打ち合わせ中に動かすのは、条件を変えた再実行だけにする。
- 同じボタンの連打は、実行中の `analysis_runs` があれば新しい実行を作らない。

## 9. テスト
- 集計の部品：小さな固定データ（町丁目3つ、取引10件 など）で「この入力ならこのカードになる」を確かめる。
- ルールエンジン：狙う層・訴求・予算配分それぞれで、条件と効果の組み合わせごとに期待する結果になるか確かめる。同点・全員低得点・指標欠損のケースも。
- 検証：作られた数字を含む文章、四捨五入の差がある文章、比べる値のない比較語、未入力の設備を言う文章を用意し、正しく見分けられるか確かめる。
- AIの文章：テスト物件で、検証を通る割合を記録する（P3、本番の要件の材料）。
- 性能・費用：応答時間（p50/p95）、トークン、1物件あたりの費用を記録する（P7）。
- Basic認証：認証なしでは `/api` を含む全ページが開かないことを確かめる。

## 12. 確認が必要なこと・残っている課題

**BRUMBY様・社内に確認する**
- 評価の尺度（10章の叩き台でよいか）
- 狙う層の判断に使う閾値（徒歩距離、将来人口の増減など）
- 総予算の決め方（物件価格の何%か、固定額か。入力がないときの提案値に使う）
- 訴求の素材と、それぞれの選ぶ条件（6.4は叩き台）
- 聞き取り用の質問シートを別に作る（閾値・総予算・訴求の素材をまとめて聞く）
- テスト物件の情報をAIに送ることの了解（D28）
- 社内への報告：Cloudflare→Vercel、D1→Supabase、AI Gatewayを使わない、評価者はBRUMBY様のみ

**技術**
- VercelのプランごとのAI生成の実行時間の上限（超えるなら処理を分割する。D34）
- Supabaseの料金プラン（無料プランの一時停止を避けるため、PoCの間は有料プランを想定）。契約前に公式で確認する
- Anthropic APIのデータ保持・学習条件の確認（D28）
- OSM（ODbL）の保存・出典の条件、商業施設データの網羅度
- BRUMBY様のテスト物件は秘密保持契約の対象：プロジェクトのメンバーを絞る。`service_role` キーは共有しない
