## 3. 版（`dataset_versions`）の仕組み

**版＝データを1回取り込んだときの、ひとまとまり。** データの行には、すべて `dataset_version_id` が付く。

| 状態 | 意味 |
|---|---|
| `loading` | 取り込み中、または途中で失敗した。使わない |
| `active` | 今使っているデータ。同じ範囲（`source`＋`dataset`＋`coverage`）で1つだけ |
| `archived` | 前に使っていたデータ |

### 取り込みの流れ（`scripts/ingest/lib/runner.ts`）
1. 版を作る（`loading`）
2. APIから取得し、応答をそのままStorageに保存して、DBに読み込む
3. 件数と空欄の割合を数える（0件なら切り替えない）
4. 同じ範囲の古い版を `archived`、新しい版を `active` にし、`ingest_logs` に記録する（1つのトランザクションで）
5. 失敗したら、版は `loading` のまま残し、使用中のデータには触れない

### なぜ版を使うか
- 取り込みが途中で失敗しても、使用中のデータが壊れない
- 分析の結果に、使った版の番号を残す。「どのデータで出した数字か」を後から追える
- レポートの出典の「いつ取得したデータか」を、版から出す

### 決めた運用
- **古い版は、新しい版が `active` になったあとで、指示があれば削除する**（指示がなければ削除しない）
- 版を削除すると、その版の行と `ingest_logs` もまとめて消える（`on delete cascade`）。Storageの生データは別に削除する
- 同じ取引が2つの版に入るのは、切り替えから古い版の削除までの間だけ。この間に集計すると二重に数えるので、集計は必ず `active` の版に絞る
- 「`active` の版だけを見せるビュー」は、PoCでは作らない（必要になったら作る。ビューはデータを複製しないので、容量は増えない）

### データごとの版の分け方
| データ | `coverage` の例 | 更新のとき |
|---|---|---|
| 取引価格（XIT001） | `pref:15` | **全期間を取り直す**（約5分）。過去の地区コード・地区名が変わることがあるため |
| 地価（XPT002） | `pref:15/year:2026` | **年ごとに版を分け、新しい年の分だけを取る**。公表済みの価格は書き換わらないため。3月（公示）に取った年の分は、9月（調査）にその年の分だけを取り直す |
| バス停留所（国土数値情報 P11） | `pref:15` | 新しい年度のファイルが出たら、県の全件を新しい版として入れ直す |

**取得のときの注意**
- XIT001・XIT002・XCT001 以外は、すべて地図タイル単位（z/x/y、`response_format=geojson|pbf`）で取る。データがないとき、タイルのAPIは404ではなく、200と空の配列を返す
- **取れるズームの範囲はAPIごとに違う。** 確かめたもの：XPT001 は11〜15、XKT002 は11〜15、XPT002 は13〜15。ほかのXKT系は未確認なので、実装の前に各APIの詳細ページ（`/help/apiManual/xktNNN/`）で確かめる。`scripts/ingest/lib/tiles.ts` ではズームを1つに決め打ちしない
- 取得回数の上限は書かれていないが、マニュアルは「間隔を空けて呼ぶ」ように求めている
- マニュアルにXKT008・009・012はない（欠番）

### 取引価格（不動産情報ライブラリ XIT001）
- **1行＝不動産の取引1件。** いつ（四半期）、どこで（市区町村・地区名。番地はない）、何を、いくらで
- APIで取れる期間：取引価格情報は2005年第3四半期から、成約価格情報は2021年から
- 都道府県を指定して、四半期ごとに取得できる。**未公表の四半期は404が返る**（0件として扱う）
- 約半年遅れで公表される（2026-10-03の時点で、最新は2026Q1）
- 「取引価格情報」は買った人へのアンケート、「成約価格情報」は不動産会社がレインズに登録したもの。**すべての売買が載っているわけではない**（マニュアルではなく、国土交通省の一般的な説明による）
- 「面積」は、土地・戸建では土地の面積、中古マンションでは専有面積
- 坪単価（`PricePerUnit`）は列にしていない（`raw` にある）
- **地区コード（`DistrictCode`）は、データの更新で変わることがある**（マニュアル）。町丁目との対応は版ごとに作る
- 地区コード（例：`151010240`）は、市区町村コード5桁＋町のコード4桁に見える。国勢調査の町丁目のコード（`KEY_CODE`）とは**別の体系**で、先頭9桁が一致しても別の町を指す（2026-10-03に確認。下の「地区と町丁目の対応」）
- **相場に使うのは「宅地(土地と建物)」「宅地(土地)」だけ**（設計書D11）。中古マンション・農地・林地は保存するが集計に使わない。「取引の事情等」が調停・競売等、関係者間取引、瑕疵有りの可能性の取引も除く
  - 戸建ての相場（2026-10-28 決定、`docs/相場の出し方変更.md` 3.3）：用途は「住宅」を含み、ほかは駐車場・倉庫・その他だけ。**用途が空なら構造（木造・軽量鉄骨造・鉄骨造）で入れる**（成約価格情報は用途がすべて空のため）。構造も空なら外す
  - 「隣地の購入」も外す（市場で決まった値段ではない）。「私道を含む取引」は残す。延床面積は50〜300㎡
  - 成約価格情報は「取引の事情等」がすべて空なので、調停・競売等を外せていない
- マニュアル：https://www.reinfolib.mlit.go.jp/help/apiManual/xit001/

### 取引価格の地区と町丁目の対応（2026-10-03に決定・実測）
- **取引の「地区」は町・大字の単位で、町丁目より一段粗い。** 例：地区「小針台」→ 町丁目「小針台一丁目」「小針台二丁目」…。1つの地区に複数の町丁目が対応する（最大32）
- そのため、取引の行に列を足さず、**対応表（`district_areas`）を別に持つ**。理由：
  - 1対多を1つの列では表せない
  - 取引価格は四半期ごとに全期間を取り直す。対応表なら地区の数（約4,500）だけ作り直せばよく、取引の76,000行を書き直さずに済む
  - 取引の版と町丁目の版は、別々の時期に入れ替わる（国勢調査2025への切り替えなど）。対応表は「取引の版×町丁目の版」の組み合わせごとに作る
  - 手で直した対応（`district_manual`）は版に関係なく残し、作り直すたびに当てはめる
- **地区コード（`DistrictCode`、9桁）では結びつけられない。** 国勢調査の `KEY_CODE`（都道府県2＋市区町村3＋町・大字4＋丁目2）と桁の形は似ていて、先頭9桁が一致する地区も多い。しかし、指している町が違う（例：新発田市の地区「小友」のコードが、町丁目「金沢」と一致する）。別の体系なので使わない
- **名前で結びつける。** 同じ市区町村の中だけで探す。両方の名前を次のようにならしてから比べる
  - 全角・半角をそろえる（NFKC）
  - かっこ書きを外す（「栄町（さかえちょう）」→「栄町」）
  - 先頭の「大字」「字」を外す
  - 町丁目の名前の末尾の「○丁目」を外す
  - 「ヶ」「ヵ」を「ケ」に、「之」を「ノ」にそろえる
- 結びつけ方の順番と一致率（宅地の取引 51,020件に対する割合。2026-10-03、取引は版4、町丁目は版13。`npm run build:district-areas` の結果）

| 順番 | `match` | 内容 | 地区 | 宅地の取引 |
|---|---|---|---:|---:|
| 1 | `manual` | `district_manual` に書いたもの。あれば最優先 | 0 | 0% |
| 2 | `exact` | ならした名前が一致 | 4,089 | 94.3% |
| 3 | `prefix` | 町丁目の名前が地区名で始まる（「太田」→「太田栄町」「太田城山」…、「本町通」→「本町通一番町」…） | 97 | 3.9% |
| — | （対応表に行を作らない） | 結びつかない。区・市の単位の相場にだけ使う | 273 | 1.8% |

- **`prefix` は、`manual`・`exact` でほかの地区に取られた町丁目を使わない。** はじめはこの制限がなく、「横越」が「横越中央一丁目」（地区「横越中央」のもの）を、「巻」が「巻東町」を取るなど、86行の取り違えがあった。制限を入れて0にした（使わなかった町丁目は64個。町丁目が残らず「結びつかない」に移った地区は3個、宅地の取引4件）
- `prefix` で、町丁目の先頭と一致する地区が複数あれば、いちばん長い名前の地区に渡す（「礎町通上一ノ町」は「礎町通」ではなく「礎町通上」へ）
- **`exact` は「大字」「字」を外して比べるが、外さずに一致する地区がほかにあれば、その町丁目はその地区に渡す。** 例：長岡市
  - 地区「大字茨目」→ 町丁目「大字茨目」
  - 地区「茨目」→ 町丁目「茨目一〜三丁目」
  - はじめはどちらも4つ全部に結びついていた（84行の重なり）。直して重なりは9町丁目になった
- 上の理由で `exact` も `prefix` も取れなかった地区は、同じ町丁目を分け合う。例：糸魚川市「大字蓮台寺」と「蓮台寺」は、どちらも「蓮台寺一〜二丁目」（町丁目に「大字蓮台寺」がないため）
- 小千谷市「大字土川」は、`prefix` で「土川山崎」「土川上ノ島」「土川中島」に結びつく（「土川一〜二丁目」は地区「土川」へ）。大字の部分＝丁目のない部分として、自然な結果
- **読みだけ違う別の町が、同じ市区町村にある。** かっこ書きを外すと区別できず、今はどちらも同じ町丁目の全部に結びついている。どちらがどの町丁目かを確かめて `district_manual` に書く

### 地価公示・地価調査（不動産情報ライブラリ XPT002）
- **1行＝1つの地点の、1年分の価格。** 地点（標準地・基準地）は、国や県が毎年価格を調べている決まった土地
- APIで取れる期間：1995年から
- **都道府県では指定できず、地図のタイル単位でしか取れない。** ズーム13（1枚 約3.5km四方）で、新潟県を覆うには約3,000枚が必要（四角の範囲なので、海や隣の県も含む）
- タイルには隣の県の地点も入るので、都道府県コードで絞る
- 1回の応答で、地価公示（`land_price_type = 0`、1月1日時点）と地価調査（`= 1`、7月1日時点）の両方が返る
- 各地点に、前年の価格と前年からの変動率も入っている（新しく設けられた地点は空欄）
- 取り方：最新の年は全タイルを取り（`--tiles all`）、過去の年は地点のあったタイルだけを取る（`--tiles known`）。地点はほぼ毎年同じ場所なので、取りこぼしはわずかと考えている
- 新潟県の2026年：約3,000枚のうち、地点があったのは440枚。964地点（地価公示434、地価調査530）。全タイルの取得に約17分
- **林地の価格は単位が「円/10a」（1,000㎡あたり）。** 1㎡あたりの価格の列（`price_per_sqm`）には入れず空欄にする（元の値は `raw` にある）。林地の地点は、市区町村コードが `15900`（県単位の番号）になっている
- **休止中の地点**（`pause_flag = 1`）は、その年の価格が空欄（2026年の地価公示で7地点）
- 用途は、住宅地・商業地・工業地・宅地見込地・林地。相場に使うのは住宅地が中心になる
- 取引価格のある37の市区町村すべてに、地価の地点がある
- 過去の年（`--tiles known`）は、2026年の地点から割り出した297枚だけを取り、1年あたり約2分。全タイルを取った2026年（440枚）との差は、隣の県の地点しかなかったタイル
- 地点の数は、どの年もほぼ同じ（946〜970）。2015年の地点のうち2026年にも残っているのは848（約9割）で、地点は少しずつ入れ替わる
- 「地点のあったタイルだけ」で取った過去の年に、取りこぼしがどのくらいあるかは未検証（確かめるなら、過去の年を1つ選んで `--tiles all` で取り、地点数を比べる）
- 鑑定評価書のAPI（XCT001）は都道府県で指定できるが、地価公示だけ・5年分だけ・緯度経度なしなので使わない
- 取得する期間：**2015〜2026年**（取引価格の期間にそろえる）
- マニュアル：https://www.reinfolib.mlit.go.jp/help/apiManual/xpt002/

### 国勢調査2020 小地域（e-Stat API）
- **1行＝1つの地域の、1つの項目の値**（縦持ち）。項目（`stat_key`）を増やしても、列を足さずに済む
- e-Stat API の `getStatsList` で `searchKind=2`（小地域・地域メッシュ）を指定すると、小地域の表が見つかる。表は都道府県ごとに分かれていて、`statsDataId` も都道府県ごとに違う

| 男女別人口総数及び世帯総数 | 8003006731 | `pop_total`、`pop_male`、`pop_female`、`households` |
| 年齢（5歳階級、4区分）別 | 8003006774 | `age_total`、`age_00_04`〜`age_70_74`、`age_under15`、`age_15_64`、`age_65plus`、`age_75plus`（総数だけ。男女別は取っていない） |
| 世帯の家族類型別一般世帯数 | 8003006884 | `hh_general`、`hh_kin`、`hh_nuclear`、`hh_couple_only`、`hh_couple_children`（夫婦と子供）、`hh_non_nuclear`、`hh_with_under6`、`hh_with_under18`、`hh_with_65plus` |

  - level2：丁目のない町（9桁、4,343）
  - level3：丁目のある町（9桁、908）。**中身は丁目の合計なので保存しない**（保存すると二重に数える。町丁目の境界にもない）

### バス停留所（国土数値情報 P11、2026-10-12に取り込み）
- APIではなく、国土数値情報のサイト（https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P11-v3_0.html ）から都道府県ごとのzipを手でダウンロードし、中の GeoJSON（`P11-22_15.geojson`）を取り込む。シェープファイルは使わない
- 取り込み：`npm run ingest -- mlit-bus-stops --file "<GeoJSONのパス>" --pref 15`。確認：`npm run db:check-bus-stops`
- 名前・座標がない行、日本の外の座標が1件でもあれば、何も入れずに止まる
- 系統の欄1つに、複数の系統がカンマ区切りで入っていることがある（区分も同じ数だけカンマ区切り）。今は分けずに保存している
- ファイルの座標系は JGD2011（EPSG:6668）。EPSG:4326 として保存している（差は数cm以下）
- 分析で、`active` の版（県ごとに複数あってよい）から物件に一番近いバス停を探し、カード `facility.bus_stop_nearest`（直線距離）を作る（2026-10-12）。採点ルール表の「バス停_m」に使う（手入力があればそちらを優先）。探す範囲は5km（採点は800m以上をまとめて扱うため）。5km以内になければ「データ不足」。basis に事業者・系統（カンマで分けたもの）・近い順10件を残す。物件の登録のときに取りに行く XKT系と違い、取り込み済みの全件から探す
- 物件1では、上近江二丁目（新潟交通）217m → R40「バス停まで300m以内」が当たる（実行54）
- 版37（1回目の失敗、0件）は2026-10-12に削除した（Storage の元ファイルも削除）

### 物件の周りのデータ（不動産情報ライブラリ XKT系、2026-10-04に仕組みを作成）
- **物件が登録されたときに、その周りを取りに行く**（県全域を先に取らない）。処理は `lib/surroundings/fetch.ts`。物件の画面（`/properties/<番号>`）は、位置が新しくなったら（登録・ピンの保存・住所からの取り直し）自動で取りに行き、表に進み具合を出す（2026-10-07）。種類ごとに別の呼び出し（`app/(app)/properties/[id]/surroundings/route.ts`）にし、4種類ずつ同時に取る（2026-10-13。Server Actions は画面から1つずつ順にしか呼ばれないため Route Handler にした）。ターミナルで試すときは `npm run fetch-surroundings -- --property <番号>`。Vercel にも `REINFOLIB_API_KEY` が必要
- 設計書4.2の `tile_cache`（タイルを丸ごと保存）はやめて、**物件の近くの地物だけを `geo_features` に保存する**形にした。洪水浸水想定はタイル1枚で681〜2,800件・3〜11MBあり、丸ごと保存すると無料枠の容量が足りなくなるため（`tile_cache` はマイグレーションで削除）
- APIごとに取り方を分けている（`lib/surroundings/layers.ts`）

| 取り方 | API | ズーム | 保存する範囲 |
|---|---|---|---|
| 半径の中を数える | XKT006 学校、XKT007 保育園・幼稚園等、XKT015 駅、XKT013 将来人口 | 13 | 物件から半径3km |
| 物件の地点で判定する | XKT002 用途地域、XKT025 液状化、XKT026 洪水、XKT029 土砂災害 | 15 | 物件から300m |
| 物件の地点で判定する | XKT004 小学校区、XKT005 中学校区 | 13 | 物件を含む区域だけ |

- **取れるズームはAPIごとに違う**（マニュアル）：XKT002・004・005・013・015・025・029 は11〜15、XKT006・007 は13〜15、XKT026 は14〜15
- タイルのAPIは、データがないとき404ではなく、200と空の配列を返す
- どの地物にも `_id`（APIが付けたID）があるので、それで二重の保存を防いでいる。同じ物件で取り直しても、地物は増えない
- 版は、APIごとに1つ（`coverage = pref:15`）。物件が増えるたびに、同じ版に地物が足されていく。データを更新するときは、新しい版を作って取り直す
- 1物件あたり30〜55秒（10のAPI、タイル合計30〜40枚）。保存する容量は1物件あたり2MB前後（ほとんどが将来人口のメッシュ）
- **小学校区・中学校区（XKT004・005）は、新潟市と長岡市にデータがない。** 新発田市・上越市・三条市にはある（2026-10-04に確かめた）。新潟市は、市の通学区域（`school_zones`）で補うようにした（2026-10-12。data-ingest-records.md の「新潟市の通学区域」）。長岡市はまだない
- **将来人口（XKT013）は、2020年は総人口（`PTN_2020`）だけ。** 年齢別（`PT01_`〜`PT20_`）は2025年から。「子育て世代の増減」は2025年→2035年で比べる。値は小数（推計値）
- 駅（XKT015）は、地物の形が点ではなく線（ホームの形）
- 学校（XKT006）の休校区分 `P29_007`：0 調査なし、1 開校中、2 休校中（国土数値情報のコード表 ClosedSchoolCode）。最寄りの小学校を探すときは2を除く。大学・専修学校などは0（調査なし）になっている
- **最寄りの小学校＝通う学校（学区）とは限らない。** 学区は川や大きな道路で区切られることがあるので、画面では「最寄りの小学校」と書き、学区とは書かない。距離は直線なので、歩く距離の目安は ×1.3（設計書5.3）

### スーパーマーケット（OpenStreetMap、Overpass API。2026-10-12に取れるようにした）
- 物件の位置が決まったときに、XKT系と一緒に自動で取る（`lib/surroundings/osm.ts`、`api_id = OSM_SUPERMARKET`）。`shop=supermarket` の点・建物（node/way/relation）を、物件から半径3kmで取る。ターミナルでは `npm run fetch-surroundings -- --property <番号> --apis OSM_SUPERMARKET`
- 保存先は `geo_features`。`feature_id` は `<物件の番号>:<node/123 など>`。XKT系と違い、**物件ごとに入れ替える**（取り直すと、その物件の分を消してから入れる。閉店した店が残らないように）。版は `source = osm`、`dataset = supermarket`、`coverage = global` の1つ（版34）
- **Overpass は、名乗らない（汎用の User-Agent の）リクエストを HTTP 406 で断る**（2026-10-12に確認。curl・Node の fetch の既定、ブラウザ風の UA はすべて406）。アプリ名と連絡先を入れた `User-Agent: brumby/0.1 (+https://github.com/Cloud-Nature-Inc/brumby)` を付けている。これがなかったので、最初の版の処理では1件も取れていなかった
- `overpass-api.de` は混んでいると **HTTP 504** をよく返す（2026-10-12は7物件のうち4物件が1回目で504）。429・5xx のときだけ3秒空けて1回やり直す。それでもだめなら「failed」になるので、時間をおいて取り直す。ミラー（overpass.kumi.systems・overpass.private.coffee）はつながらず、maps.mail.ru も504だったので、予備の取得先は置いていない
- 取り直しが失敗すると、取得の記録（`property_fetches`）は「failed」で上書きされる（前に取れた地物は消えずに残るが、分析は記録が failed なのでカードを作らない）。XKT系と同じ扱い
- 分析のカード `facility.supermarket_nearest`（最寄りのスーパーまでの直線距離）を作り、採点ルール表の「スーパー_m」に使う（手入力があればそちらを優先）。名前は `name`、なければ `brand`、どちらもなければ「名称未登録のスーパー」（7物件の100件のうち6件）
- **OSMの `shop=supermarket` には、スーパーでない店が入っていることがある。** 物件2（寺尾）の最寄りは「ひらせいホームセンター」642m。網羅度・正しさは地域の登録者しだいなので、結果は目で確かめる
- 物件1の最寄りはウオロク 445m（直線。周り3kmに20件、実行で `facility.supermarket_nearest` が ok になったことを確認）

### 住所から緯度経度（国土地理院 住所検索API）
- `https://msearch.gsi.go.jp/address-search/AddressSearch?q=<住所>`。無料・APIキーなし。1回0.1〜0.3秒
- **細かさは住所の書き方で変わる。** 「○番○号」（住居表示）は建物のあたりまで合う（例：上近江三丁目２番１号）。「○番地」（地番）は丁目の代表の地点までしか合わないことがある（例：紫竹1丁目36番4 → 紫竹一丁目）
- 丁目の代表の地点でも、ずれは数百m以内。半径の集計への影響は小さいが、地点で判定するもの（浸水想定、用途地域）は結果が変わることがある。登録のときに地図にピンを出して確かめ、ずれていれば直せるようにする（設計書7章）
- 仮の物件1は、はじめ経度・緯度を確かめずに置いたため、上近江から約2kmずれていた。住所検索で取り直して直した（2026-10-04）
- `property_fetches.status = 'empty'` の読み方：`features_in_tiles = 0` なら「その地域にデータがない」、1以上なら「データはあるが物件の近くにない」（例：浸水想定区域の外）

- 物件の地点が区域の外なら、`value = 0`（「浸水想定区域の外」など）で `status = ok`。周りのデータを取っていない・取得に失敗した物件は `not_available`

**④ 周辺施設の決まりごと**
- 最寄りの施設は、周りのデータを取った範囲（半径3km）の中で、近い順に探す。見つからなければ `insufficient`
- 距離は直線。徒歩の目安は直線×1.3、分速80m（`basis` に直線・徒歩の距離と分数を残す）
- 小学校・中学校は、学校の分類（`P29_003_name_ja`）で絞り、休校中（`P29_007 = 2`）を除く。**最寄りの学校が通う学校とは限らない**（`basis.note` に書いている）
- 学区は、物件の地点を含む区域。その地域にデータがなければ `not_available`（理由：「この地域には小学校区のデータがありません」）
- **新潟市は、市の通学区域（`school_zones`）で補う**（2026-10-12）。XKT004・005 の `features_in_tiles` が0（または周りのデータが取れていない）で、住所が新潟市のとき、住所の町名・丁目・番地で一覧表を引く。`scope.type = address`、`basis` に町名 `town`・丁目 `chome`・当たった行の地番等 `lots`
  - 番地によって学校が分かれ、住所からは1校に決められないときは `insufficient`。`value_text` は「関屋中学校または小針中学校（番地で異なる）」、`basis.candidates` に候補
  - 町名が一覧表にないときは `not_available`（理由に住所の町名を書く）
  - 地番の書き方が複雑な行（枝番・甲乙など。158行）は範囲を読み取らず、候補から外せないものとして扱う
  - 物件の画面の「周辺の情報」の表でも、小学校区・中学校区が「データなし」の行に、同じ引き方の結果を添える（「市の通学区域（住所から）：上山小学校」）。引き方は `lib/school-zones/lookup.ts` にまとめ、分析と画面で共通に使う
- 保育園・幼稚園等の数は、施設を数える半径（初期値1km）の中。`basis.kinds` に内訳（保育所等・幼稚園・認定こども園）。保育所は分類名がないので「保育所等」とまとめている
- 駅は、最寄りの駅の全路線と、乗降客数（人/日、乗る人と降りる人の合計）の最新の年。乗り入れる路線が複数ある駅は、中心の1路線の地物にだけ数が入っている（重複コード 1：当該路線駅に記載、2：他路線駅に記載。データ有無コード 1：データ有）。年ごとに4項目ずつ（`S12_006`＋4k が重複、`007`＋4k が有無、`009`＋4k が乗降客数、k＝0 が2011年）。2026-10-04の時点で、最新は2023年
- 用途地域は、物件の地点を含む区域。なければ「用途地域の指定がない区域」（市街化調整区域などの可能性）。新潟市のデータには建蔽率・容積率が入っていない（三条市は入っている）

**① 人口構成の決まりごと**
- 物件を中心にした円（中心部1km、郊外・周辺3km）と重なる町丁目ごとに、「重なった面積 ÷ 町丁目の面積」（w）を出し、国勢調査の値に w を掛けて足す。割合は「足した分子 ÷ 足した分母」
- 比べる値は、物件の地点を含む町丁目の市区町村（新潟市は区）の値
- 分母（人や世帯の数）が50未満なら `insufficient`（割合がぶれやすいため）
- 狙う層の年齢は、国勢調査の5歳ごとの区切りに合わせる（30〜49歳なら 30〜34・35〜39・40〜44・45〜49 の4つ）。条件の `target_age` を変えると、カードの名前（`target.age_30_49_ratio`）も変わる
- 割合の分母：年齢は総数（年齢不詳を含む）、世帯は一般世帯、民営借家は住宅に住む一般世帯、一戸建は主世帯
- **確かめたこと**：半径50mの円（上近江三丁目の中に収まる）で分析すると、上近江三丁目そのものの割合と一致した（30〜49歳 30.0%、18歳未満のいる世帯 25.9%、夫婦と子供 31.2%、民営借家 30.8%、一戸建 24.5%）。半径1kmの人口（21,226人）は、将来人口のメッシュで数えた2020年の人口（21,393人）と1%以内で合った
- 面積で割り振るので、町丁目の中で人が偏って住んでいる場合（大きな公園や工場がある町丁目など）は誤差が出る

**② 将来人口の元のデータ**
- APIは不動産情報ライブラリの XKT013。中身は国土数値情報「250mメッシュ別将来推計人口データ（R6国政局推計）」（国土交通省 国土政策局、2024年度作成、オープンデータ CC BY 4.0）
- もとにしたデータ：総務省「令和2年国勢調査」（調査票から独自に集計）、国立社会保障・人口問題研究所「日本の将来推計人口（令和5年推計）」「日本の地域別将来推計人口（令和5年推計）」の推計値と仮定値（生残率、子ども女性比、純移動率）
- 2020年の実際の人口を出発点に、市区町村ごとの「生まれる・亡くなる・引っ越す」の仮定を250mの区画に当てはめた**推計値**。2070年まで、5年ごと・5歳ごと
- 2020年より後の開発（新しい住宅地など）は入っていない。過去の傾向が続くことが前提。レポートでは「国の推計では…見込み」のように、推計であることがわかる書き方にする
- 説明のページ：https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-mesh250r6.html

**② 将来人口の決まりごと**
- 物件の周りのデータで取った将来推計人口250mメッシュ（XKT013、半径3km）のうち、メッシュの中心が集計の半径（中心部1km、郊外・周辺3km）の円に入るものを足す
- 2025年→2035年の増減の割合（2035年 ÷ 2025年 − 1）。年齢別が2025年からなので、起点は2025年
- 3枚のカード：総人口（`PT00`）、狙う層の年齢（30〜49歳＝`PT07`〜`PT10`。PTの番号は「年齢÷5＋1」）、0〜14歳（`PTA`）
- 人が少ないメッシュは秘匿され（`HITOKU` = `*`、値は0）、その値は近くのメッシュ（`@`）に合算されている。合算後の値をそのまま足す（新潟県の3物件の周りで、秘匿は15メッシュ・計28人ほど）
- 集計の半径が、周りのデータを取った範囲より大きいと `insufficient`。2025年の人数が50人未満でも `insufficient`
- **確かめたこと**：物件1の30〜49歳（5,973人 → 4,671人）を、項目名を1つずつ書いた別の問い合わせで数え直して一致した。半径1kmに入ったメッシュは48個で、円の面積から見込む約50個と合う。2025年の総人口（21,435人）は、国勢調査2020年を面積で割り振った人口（21,226人）と近い

**③ 相場の決まりごと**
- 物件の種類 → 取引の種類：新築戸建・中古戸建は「宅地(土地と建物)」、土地は「宅地(土地)」（D11）。新築と中古は取引のデータでは区別できない
- 期間：取引データの最新の四半期から、さかのぼって3年分（2026-10-04の時点で 2023Q2〜2026Q1）
- 範囲：物件のある地区 → 隣の地区まで → 区・市 と、10件以上になるまで広げる。どこまで広げたかを `scope.level` に、各段階の件数を `basis.tried` に残す
  - 物件のある地区：物件の地点を含む町丁目に、対応表（`district_areas`）で結びつく取引の地区
  - 隣の地区：物件のある町丁目と境界が接している町丁目（境界のわずかな隙間を考えて約5m以内）に結びつく地区を足したもの（2026-10-04に決定）
  - 区・市：物件のある市区町村（新潟市は区）の全体
- 除く取引：調停・競売等、関係者間取引、瑕疵有りの可能性（D11）。取引価格情報と成約価格情報は両方使う
- 中央値と四分位（25%・75%）は万円で表示。物件の価格との差（`market.price_gap`）は「物件の価格 ÷ 中央値 − 1」
- 新築戸建には、築5年以内（最新の年−5年以降の建築）の取引に絞った中央値も並べる（`market.recent_build_price_median`、同じく範囲を広げる）
- 土地には、1㎡あたりの取引価格の中央値も出し、物件の1㎡あたりの価格と比べる
- 地価の推移（`land.trend_5y`）：物件から3km以内で、今年と5年前の両方に価格がある住宅地の地点を近い順に5つ選び、同じ地点どうしの変化率を平均する。比べる値は、物件のある市区町村の同じ条件の地点すべての平均
- 最寄りの住宅地の地価（`land.nearest_residential_price`）：上の5地点のうち一番近い地点の今年の価格
- **確かめたこと**：物件1の「物件のある地区」（上近江、10件、中央値2,450万円）を、別の問い合わせで数え直して一致した

**③ 相場で、あとで詰めること**（まずは動く形を優先した）
- 全部の築年数を混ぜた中央値は、新築戸建には低く出る（物件1：全体2,450万円、築5年以内4,550万円）。どちらを主に見せるか
- 極端な取引（物件1の地区には3億2,000万円の取引がある）。中央値なので影響は小さいが、外すか
- 10件ちょうどで止まると、四分位の幅が広い（物件1：1,225〜3,675万円）。件数の目安を増やすか
- 土地の面積・建物の面積をそろえた比較（面積あたりの価格）をするか
- 成約価格情報（不動産会社の登録）と取引価格情報（アンケート）を分けて見せるか

**⑥ 競合物件の決まりごと**
- 競合物件は手入力（物件ごとに3件まで、`competitors`）。入力がなければ `not_available`（理由：「競合物件が入力されていません」）
- 価格の差：物件の価格 ÷ 競合の平均価格 − 1。`basis` に競合1件ずつとの差も残す
- 面積あたりの価格の差：戸建は建物の面積、土地は土地の面積で割った価格どうしを比べる
- 土地の面積の差：物件の土地 ÷ 競合の平均 − 1
- 特徴の一覧：物件と競合の間取り・駅からの徒歩・駐車場・特徴を並べる。「何が違うか」の言葉づくりはAIが行う（設計書6.2）
- 公開データを使わないので、`dataset_version_ids` は空。出典は「手入力」
- **確かめたこと**：物件1（試しの競合3件）で、平均価格3,880万円・差 −2.6%、建物1㎡あたり356,671円と平均368,019円、土地180.25㎡と平均157.7㎡を、手の計算で確かめた
- 仮の物件1の競合3件は、プロトタイプの見本（`app/_lib/data.ts` の `compData`）と同じ値。物件1には、見本に合わせて間取り4LDK・駐車場2台・ZEH仕様・最寄り駅 徒歩12分も入れた

### 採点ルール表（2026-10-12に、狙う層・訴求・予算・媒体の決め方を置き換え。設計書 D35）

### ルール表とルールエンジン（2026-10-04に作成。2026-10-12から使っていない。採点ルール表に置き換え）
- 分析の流れで、事実カードを作ったあとに、ルールで判断して**判断カード**（`kind = decision`）を足す。実行の段階（`analysis_runs.stage`）は `rules` になる。処理は `lib/rules/engine.ts`
- 狙う層の候補と媒体の一覧は `lib/rules/catalog.ts`（プロトタイプの `targetList`・`mediaDefs` が出発点）
  - 狙う層：`family`（30〜40代の子育てファミリー）、`dinks`（20代後半〜30代前半の共働き夫婦）、`relocation`（周辺エリアの住み替え層）
  - 媒体：`sns`（Instagram・Facebook広告）、`posting`（ポスティング）、`flyer`（チラシ制作・印刷）、`lp`（物件専用LP）
- **ルール表の画面（`/rules`、設計書D14）**：ルールを「もし〜なら → 〜」の文で一覧にし、**追加・変更・削除**ができる。変更の履歴（新しい順に30件）も表示する。ログインはないので、打ち合わせの場でクラウドネイチャーのPCで動かす
  - 追加・変更のフォーム：ルールの種類 → 条件（なし／1つ／2つで両方当てはまるとき）→ 効果 → 理由・使う/使わない・直した人。条件の「何を見るか」は一覧（`lib/rules/describe.ts` の `FACT_OPTIONS`、26項目）から選ぶ。カードの key を手で打たないので、打ち間違いでルールが黙って効かなくなることがない
  - 比べる相手は「区・市の値」（割合のカードだけ。○ポイント以上 多い／少ない）か「決まった値」（以上・より大きい・以下・未満）。割合の決まった値は % で入力し、保存するときに100で割る
  - 保存の処理（`app/(app)/rules/actions.ts`）は、入力をサーバー側で必ず確かめる（一覧にない値、区・市と比べられない値との比較、空の理由などはエラーにして、画面に理由を出す）
  - 新しいルールの番号は「R-」＋今ある一番大きい番号＋1
  - 削除は確認のダイアログのあとに行い、変更の履歴に削除前の内容が残る。外すだけなら「このルールを使う」を外すほうが安全
  - 「総予算（先に決めた額）」は、総予算を決めたあとに計算する媒体の重み・固定額・最低額のルールでだけ使える（狙う層の点数のルールでは、まだ決まっていない）
  - 2026-10-04に、追加（R-49、使わない状態）→ 条件の変更（浸水深ランク → 地価の5年間の変化、区・市の値より5ポイント以上多い）→ 削除を画面で行って確かめた。R-32 は値を変えずに保存して確かめた（版2）。どちらも分析の結果は変わっていない
- 仮のルールは `npm run seed-rules` で入れる（`scripts/seed-rules.ts`、20件）。**すでにある番号のルールは上書きしない**ので、Supabase の画面で直した内容は消えない。直すと `version` が上がり、変更が `rule_revisions` に残る
- 計算の手順（毎回同じ）
  1. 狙う層：候補ごとに、当てはまったルールの点数を足して順位を出す。同点なら一覧の順
  2. 総予算：当てはまったルールの額。複数あれば一番大きい額
  3. 媒体：出発点の重み（`weight`）→ 当てはまったルールの倍率（`multiply`）を掛ける → 固定額（`fixed_man_yen`）→ 最低額（`min_man_yen`）→ 残りを重みの比率で分ける → 千円単位に丸め、端数は一番多い媒体で合わせて、合計を総予算にそろえる
  4. 効いたルール（番号・版・理由）を、判断カードの `basis` に残す
- 条件の書き方（`rules.condition`）
  - `{"always": true}`：いつも当てはまる
  - `{"fact": "<カードのkey>", "op": ">", "than": "comparison", "delta": 0.03}`：カードの値 ＞ 比べる値＋0.03
  - `{"fact": "<カードのkey>", "op": "<=", "than": 800}`：カードの値 ≦ 800
  - `{"all": [条件, 条件]}`：すべて当てはまる
  - `fact` には、カードの key のほかに `property.price_man_yen`（物件の情報）と `decision.total_budget`（先に決めた総予算）も書ける
  - 参照するカードがない・データが足りない（`status` が ok でない）ときは「当てはまらない」
- 効果の書き方（`rules.effect`）：狙う層 `{"target": "family", "score": 2}`、総予算 `{"total_man_yen": 30}`、重みの出発点 `{"media": "sns", "weight": 12}`、倍率 `{"media": "sns", "multiply": 1.5}`、固定額 `{"media": "lp", "fixed_man_yen": 0}`、最低額 `{"media": "flyer", "min_man_yen": 2}`
- **仮のルールの中身**：総予算は物件の価格で決める（2,000万円未満 10万円、3,500万円未満 20万円、それ以上 30万円）。媒体の重みの出発点は、プロトタイプの配分表で総予算30万円のときの 12・7・5・6万円。総予算10万円以下ではLPを0円。チラシは最低2万円。狙う層は、子育て世帯・夫婦と子供・民営借家・一戸建の割合（区・市との比較）と、最寄りの小学校・駅の距離で点数を付ける
- **確かめたこと**：物件1の媒体の配分（15.6・6.5・3.6・4.3万円）と狙う層の点数（子育てファミリー4点）を、手の計算で確かめた
- 判断カードの比べる値は、比較した値をカードに入れたときの丸め（小数第3位）で比べる。物件1の民営借家は 0.415 と 0.415 で同じとみなされ、R-44 は効かなかった

## 7. 容量（無料枠）

| | 使用量（2026-10-03） | 無料枠の上限（要確認） |
|---|---|---|
| DB | 202MB（2026-10-04。取引価格 86MB、国勢調査 51MB、地価12年分 20MB、町丁目の境界 18MB、物件の周り 5MB など） | 500MB |
| Storage | 約46MB | 1GB |

- 上限の値は変わることがある。ダッシュボードの Usage か、Supabaseの料金ページで確かめる
- 全部のデータを入れたときの見込み：250〜300MB
- **行を削除しても、ファイルの大きさはすぐには減らない。** 大量に削除したあとは `VACUUM FULL <テーブル>` で空きを返す（実行中はそのテーブルを読み書きできない。`transactions` で16秒）
- 足りなくなったら、DBの `raw` 列をやめる（Storageに同じものがあるため。取引価格で約50MB減る）
- **無料枠は、1週間アクセスがないと一時停止する。** データは消えず、ダッシュボードから再開できる。デモの前に動いているかを確かめる

## 8. よく使うコマンド

```bash
# DBにつながるかを確かめる（バージョンとテーブルの一覧）
npm run db:check

# 取引価格（全期間を取り直す）
npm run ingest -- reinfolib-transactions --pref 15 --from 2015Q1

# 地価（最新の年は全タイル、過去の年は地点のあったタイルだけ）
npm run ingest -- reinfolib-land-prices --pref 15 --year 2026 --tiles all
npm run ingest -- reinfolib-land-prices --pref 15 --year 2025 --tiles known

# 町丁目の境界（e-Stat 国勢調査2020 小地域。APIキー不要）
npm run ingest -- estat-boundaries --pref 15

# 取引価格の地区と町丁目の対応表を作り直す（取引価格を取り直したとき、町丁目の版を切り替えたとき、district_manual を直したとき）
npm run build:district-areas

# 国勢調査2020 小地域の数字（5つの表。--tables population,age で表を絞れる）
npm run ingest -- estat-census --pref 15

# 物件の周りのデータ（XKT系）を取る（--apis XKT006,XKT026 でAPIを絞れる）
npm run fetch-surroundings -- --property 1

# 地価を範囲を絞って試す（範囲は 西,南,東,北 の経度・緯度）
npm run ingest -- reinfolib-land-prices --year 2026 --bbox 139.0,37.88,139.1,37.95

# 採点ルール表（Excel）を取り込む（--dry-run で件数と注意だけ見る）
npm run import-scoring -- "C:/Users/.../採点ルール表_初版.xlsx"

# 採点の計算のテスト（SCORING_XLSX を入れると Excel 本体でも確かめる）
npm test

# マイグレーションの状況（手元とクラウドの差）
npx supabase migration list

# マイグレーションを共有DBに反映する（確認の画面が出るので、自分で実行する）
npx supabase db push
```

- `npm run ingest` の `--` の後ろは、npmではなくスクリプトに渡される
- 受け取る引数はデータごとに決まっている。知らない引数（打ち間違い）は、DBに書き込む前にエラーで止まる
